# 招式数据、取消规则与角色连段：执行路径

日期：2026-09-18

状态：执行计划；规则访谈尚未开始，本文的建议不等于已接受的战斗规则。本文交付不包含代码实现、测试执行或正式实施票据。

## 目标与顺序

在现有战斗会话和招式资源上，形成一套可独立配置、可逐帧验证、可供真人调校的角色招式设计。

推荐路径：**角色招式定位 → 取消规则 → 数据语义与效果范围 → 正式规格与拆票 → 一条地面路线完整实现 → 浮空路线及其他效果 → 联合验收与调校。**

先确定每招的用途和预期连接，再决定数据需要表达什么；具体帧数在规则收敛后以初稿进入实现，并通过回放和试玩调整。无需先重写招式系统，也无需一次设计完整格斗游戏的全部效果。

技能路径：`ask-matt → grill-with-docs → to-prd → to-issues → implement`。只在某个问题无法通过讨论确定时进入 `prototype`；独立目录原型使用 `handoff` 带出问题、带回结论。旧路由文档中的 `to-spec / to-tickets` 在本次执行中分别对应当前可用的 `to-prd / to-issues`；产物仍遵循本仓库本地 Markdown 约定。

## 2. 用 grill-with-docs 收敛设计

在当前设计任务中按以下轮次推进。代理核对代码事实、提供选项和边界例；用户决定角色体验及规则扩展。每轮只解决当前依赖已满足的问题。

| 轮次 | 需要解决的问题 | 交付与完成条件 |
| --- | --- | --- |
| A：角色定位与招式职责 | 角色希望鼓励什么操作节奏？哪些招式负责起手、连接、浮空、收尾或其他用途？ | 一张首版招式职责表；每招有用途，明确本轮保留、调整和暂不加入的能力 |
| B：取消资格与路线 | 沿用命中确认还是增加被防/挥空取消？逐招目标还是类别规则加例外？是否自取消、反向取消、必杀/跳跃取消？ | 取消条件矩阵与路线图；每条边写明触发条件、计时起点、窗口和目标限制，至少各有一个允许例与拒绝例 |
| C：效果与数据语义 | 招式级 Hitstop 如何声明？是否需要独立防御硬直？首个无敌招式覆盖何种攻击、哪些帧？哪些命中效果本轮实际使用？ | 字段语义表和具体招式样例；明确类型、单位、时间基准、必填/默认、非法组合及运行时应用时点 |
| D：帧数与连段初稿 | 每招的启动、活跃、恢复、硬直、击退、停顿和取消窗口如何服务其职责？期望哪几条路线成立、哪些不成立？ | 首版帧表与代表路线验收表；每个待实施字段有初值，未定项显式列出 |

B 轮沿用当前“只有命中确认才获得主路线取消资格”的基线；只有用户提出扩展时才重新决定。BB/GG 的 gatling 在本计划中表示参考方向，不直接套用未指定作品或版本的规则。若需要复刻具体机制，再针对所选版本做资料研究。

取消需要表达的是“什么情况下、什么时点、可以转入什么”，单一 `can_cancel` 布尔值不足以承载这些关系。首轮建议继续使用显式目标列表；是否引入招式类别及例外规则，由实际重复配置需求决定。

将以下三个概念分开：

- **取消许可**：规则允许打断当前动作进入目标动作。
- **连段成立**：后续攻击在目标恢复前实际命中，还受距离、姿态和运动影响。
- **普通连接**：当前动作完整结束后再出招；当前运行时与 Solver 有相应限制，若要支持或扩大搜索，作为独立范围决策处理。

属性同样需要分别定义：攻击分类描述如何防御或判定；无敌描述角色在哪个时间窗免受哪些攻击；命中效果描述命中后如何改变目标。先定义行为，再选择字段或子资源结构；本阶段不预设通用“词条解释器”。

决策记录建议集中到本目录 `design-decisions.md`，标明已接受/待定/延期和来源。确定的领域术语更新 `CONTEXT.md`；有真实架构取舍时才增加 ADR。完成条件：本轮实现范围内没有阻塞实现的开放规则；延期项有清楚边界。

## 4. 固化规格，再拆成可演示的切片

设计收敛后，使用 `to-prd` 将已接受决策整理为本目录 `spec.md`，再用 `to-issues` 写入本目录 `issues/`，一文件一票。沿用 `docs/agents/issue-tracker.md` 的状态及阻塞约定。

规格应含招式职责表、取消矩阵、效果字段语义、首版帧表、代表路线、非法数据处理和验收边界。普通取消与 jump cancel、Hitstop 输入、落地恢复、自然受身继续遵循现有约束；需要变更时明确指出被替换的规则。

下面是候选切片，不是已发布票据。按最终设计调整粒度和依赖：

## 5. 实现与参数调校

每票使用 `implement`，读取正式规格与真实前置完成状态。涉及计时、取消、无敌或受击的新行为，先写可观察结果的回归案例，再实现；简单资料更新做内容检查即可。

第一条地面路线建议从现有 `5A → 5B → 5D` 出发；浮空样本从现有 `5A → 236C → jump cancel → jA → jB → jD` 出发。这些是基线候选，最终路线由 B、D 轮决定。

每条代表路线记录：起始距离、双方姿态与面向、真实输入帧、动作接受帧、首个 active、命中帧、取消帧、目标自然恢复帧、命中数和伤害。区分物理帧与不包含 Hitstop 的正常帧；当前打击 startup 表示判定出现前的等待，不能直接把外部作品的“发生 N 帧”抄入字段。

时序通过后进行不钉位、保留真实击退的回放。已有证据中，地面样本 70px 可接通，完整空中样本 48px 可接通而 70px 不成立；这些距离仅是回归起点，不是新帧表的空间保证。

调校一次改变一个有明确目的的参数组，记录改动前后与玩家反馈。自动回放证明可复现，真人试玩验证节奏及输入容错；两者分别报告。设计要求无法纸面确定时才做小原型，已有训练场足以比较的数值直接通过受控实验验证并保留最终选定值。

每票完成条件：正反例及受影响回归通过、运行时和 Solver 结论一致或明确标注未支持范围、规格与项目约定 review 完成、票据记录实际验收证据。参数改变后重新验证受影响路线和循环；不以任意命中数或总时长上限掩盖循环。

## 6. 联合验收与最终交付

| 验收面 | 必须取得的证据 |
| --- | --- |
| 文件驱动 | 实际修改同一招式资源，训练场与 Solver 都体现变化；非法数据给出可定位错误；实验文件恢复或明确保留选定参数 |
| 取消边界 | 命中/被防/挥空分别按最终规则处理；窗口首末帧、晚一帧、合法/非法目标、缓存与 Hitstop 边界均有正反例 |
| 无敌及特殊效果 | 对本轮实际加入的性质，验证开始/结束帧、攻击类别、命中结果及恢复；仅有标签或字段不算交付 |
| 连段路线 | 地面和浮空代表路线双面向真实输入回放；明确距离和失败断点；时序结论、静态空间检查、真实击退回放分别呈现 |
| 既有约束 | pre-jump、空技着地恢复、自然受身与有限空中资源仍符合规则；当前版本没有已证明的有效无限路线 |
| 真人体验 | 记录本轮输入确认、节奏、收尾反馈及蹲姿修复复玩结果；未取得的反馈保留待验收 |

全量检查使用既有 `tools/run_acceptance.ps1`，给本轮指定新的输出目录，避免覆盖旧证据：

```powershell
./tools/run_acceptance.ps1 -Output '.scratch/ftg-move-design/acceptance/final'
```

按仓库实际引擎位置使用默认路径或传入 `-Engine`。Solver 入口与范围参考现有使用指南。实现阶段先运行针对性验证，最终集成再执行全量检查；本次纯文档交付不运行战斗测试。

最终材料按需产生在本目录：

- `design-decisions.md`：设计决策、依据与延期项。
- `spec.md` 和 `issues/`：正式范围、可领取切片及阻塞关系。
- `frame-data.md`：选定的招式帧表与取消图，并注明与资源核对的版本。
- `acceptance/report.md`：自动化、真实输入回放、真人试玩和剩余限制。

面向玩家的最终操作说明更新到现有 `docs/move-data.md`、`docs/solver-guide.md` 和相关训练指南，避免同时维护互相冲突的规则表。
