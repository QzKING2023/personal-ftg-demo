# Solver 性能诊断：票据 09

## 结论

票据 09 的超长任务不是单纯的进程并发问题。真正的增长来自两个搜索面：

1. 循环证明把每圈的可调空中/落地接缝组成笛卡尔积。每个 jump 槽最多 41 个等待值；证明模式故意没有 64 叶预算，边数增长会产生 `41^N` 个完整 CombatSession 重放。
2. 可读路线先枚举所有不超过 8 招的简单路径，再对每条路径做最多 64 个延迟向量重放。09 的弹地入口和追击边使路径叶数量明显增加；缓存只能帮助重复请求，不能限制第一次请求。

后台验收证据保存在 `stopped-processes.json` 和 `process-costs.json`：其中一个 09 worker 的 CPU 累计约 5.1 小时，说明瓶颈确实发生在单个 worker 内。

## 已落地的项目级防线

- 循环证明增加真实前缀剪枝：如果下一个未赋值延迟槽输入发生前，CombatSession 已经断链或结束，整个延迟子树共享该结果。它不改变搜索预算、命中数或帧上限；前缀快照仍来自真实会话。
- 对包含 `GROUND_BOUNCE`/滑行反应的结构循环增加状态不变量：每圈至少包含一次有效 HIT，`time_scale` 严格乘以小于 1 的配置倍率，并且 `settlement_state` 明确包含该值，因此回边不可能重现。只有倍率被改成 1 或非法值时才回退到完整回放搜索。
- 可读路线最多输出 16 条叶路线。达到上限会在报告 notes 中标记路线集合未完成；已输出路线仍完成逐帧验证，接续边和循环结论不因该报告上限而伪造完整性。

这三层保证未来继续增加连段边时，单个请求不会再次无界增长：循环证明使用不变量/前缀剪枝，路线报告使用显式、可观察的报告预算，跨请求缓存和并行只作为额外加速。

## 验证

- `tests/test_bounce_corrections.gd`：全部通过。
- Godot 编辑器无脚本解析错误。
- `tests/test_solver_cycles.gd`：旧版地面循环测试仍会执行完整延迟重放，当前约 78 秒/10 次 solve；这是未使用弹地不变量的兼容路径，后续可单独迁移到通用状态图缓存。票据 09 的弹地循环路径不再进入该指数搜索。

## 未完成的边界

路线报告上限会让极密招式表的路线集合标记为未完成；报告不能把这类集合称作穷尽。若需要完整路线清单，应先使用边/状态图导出器，而不是解除上限重新运行无界枚举。
