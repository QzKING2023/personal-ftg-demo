# FTG Demo 下一阶段执行路径

日期：2026-09-14

状态：执行路径草案。本文规定工作顺序与阶段交付；具体规则、数值与正式 issue 尚未确定。

目标：修复空中操控、HUD 和搓招问题，补齐命中停顿、蹲下、防御、普通投与动作帧定义，建立本地招式数据和可操作的 Combo Solver 工作流程。

旧连段系统的 issue 01–07 保留为上一阶段记录。新阶段使用本目录，正式规格拟写入 spec.md，正式 issue 拆分后按仓库约定写入 issues/，从 01 重新编号。

**1. 恢复可测试性，建立故障复现**

使用流程：简单 HUD 修复直接实施；搓招问题使用 `/diagnosing-bugs`。本阶段可以与第 2 阶段的规则讨论并行。

- 运行现有战斗会话、训练场集成、Solver 测试，保存基线结果；已有失败与本轮引入的失败分别记录。
- 修复键位提示与战斗状态重叠，更新 README 的实际操作说明。动作 A/B/C/D 对应键盘 J/K/L/U；数字方向采用相对面向的记法。
- 增加用于诊断的输入记录：物理键、相对方向、面向、识别招式、缓存状态和接续结果。训练场展示玩家需要的信息，详细记录用于复现。
- 分别复现左/右面向的 236C、地面中立的 214D、出招期间的 214D；区分未识别、已识别但不能接续、成功出招但未命中。
- 用跳跃后松开水平键、按反方向、输入方向序列和空中出招，记录横向速度与面向变化。把用户已明确的空中动量与锁向要求转成回归案例。
- 对已证实且预期明确的缺陷直接修复；涉及尚未确定的地面面向或新指令规则的改动，随第 2 阶段的相应决策实施。

交付：可读的训练场、准确键位表、最小故障复现及诊断结论。建议记录在本目录的 diagnosis.md。

完成条件：在项目设计分辨率与用户常用窗口尺寸下提示不重叠；每个搓招故障都有可重复输入序列及明确失败阶段，修复案例有验证结果。

**2. 用 `/grill-with-docs` 确定规则**

由代理核对代码事实、提出建议和边界案例，用户决定体验与范围。按下表的依赖顺序讨论，不把待定项直接写成已接受规则。

| 轮次 | 要解决的决策 | 应形成的具体材料 |
| --- | --- | --- |
| A：面向与输入 | 地面是否始终面向对手；何时转身；跳跃越过对手后如何处理；方向序列如何按面向解释；同时按键、指令优先级与容错 | 面向规则、输入识别规则和左右镜像案例 |
| B：战斗计时 | 帧从 0 还是 1 计数、发生帧如何定义；Hitstop 从哪帧开始/结束；双方哪些状态冻结；输入何时记录、过期和消费；取消窗口使用什么计时 | 帧序表，以及各状态/计时器在停顿期间的处理表 |
| C：跳跃与移动动作 | jump 的准备、离地、滞空、落地恢复；普通跳跃与 jump cancel 的关系；空中攻击最早可开始帧；66/44/high-jump 的行为、帧数和本轮实装范围 | 行为帧数表、允许取消的阶段和有限空中资源规则 |
| D：蹲防投 | 蹲下转换；站防、蹲防、空防对各攻击属性的判定；防御硬直与防御停顿；普通投输入、发生、距离、拆投窗口和投无敌 | 防御判定矩阵、普通投规则、训练木桩测试场景 |
| E：招式与动作数据 | 输入、姿态、三段帧数、判定区域、命中/防御结果、取消条件与目标、运动效果、特殊性质；文件格式、默认值与非法数据处理 | 数据格式草案及普通技、搓招、空中技、投和 jump 的样例 |
| F：连段与 Solver | 是否扩大到收招后的普通连接；搜索起手与初始条件；只验证时序还是也验证距离/碰撞；命令入口和操作说明形式 | Solver 能力边界、输入参数、结果样例和回放验收场景 |

已明确、无需重复征求确认的方向：普通空中运动保留起跳横向速度，玩家方向输入不能主动改变空中横向速度或面向；加入命中停顿以改善确认和缓存体验；修复提示遮挡；运行时和 Solver 共用本地招式数据。

建议待定方案：地面中立时面向对手，后退不转身；碰撞和招式明确配置的运动效果单独规定。跳跃取消保留“先跳、再输入空中攻击”的操作；取消资格与空中招式选择分别定义。以上建议尚未被用户接受。

数据设计沿用现有 MoveData 的基础，避免同时重写全部战斗逻辑。先确定字段语义，再选择保存格式。跳跃、冲刺等非攻击动作也应有明确数据定义，可与招式共享基础类型，但不强迫它们拥有无意义的伤害字段。

每项新定义写入适当文档：领域术语进入 CONTEXT.md，具体规则和数值进入规格材料；确有架构取舍时记录 ADR。需要修订既有约束时明确引用原决策，特别是帧序、命中确认取消和 Solver 范围。

完成条件：每个行为都有输入、合法状态、阶段/帧数、取消条件和至少一个边界案例；所有数值具有首版值，不能只写“可配置”。

**3. 仅对无法纸面确定的手感使用 `/prototype`**

本阶段是条件分支，不是必经步骤。例如，比较几组 Hitstop 与缓存配置，或普通跳跃与 jump cancel 的起跳准备/落地恢复。

每次只回答一个问题，固定相同输入和起始条件，观察手感与帧级结果。最终选定的数值和理由回写规格材料。若需要在独立目录进行原型工作，按 `/handoff → /prototype → /handoff` 带回结论。

完成条件：明确选用的行为与初始参数，能够进入正式实现；原型不成为与战斗会话并行维护的第二套正式规则。

沿用三个已存在的主要验证边界：战斗会话逐帧输入与可观察事件、训练场真实输入适配和呈现、Solver 分析结果。数据加载通过可观察行为验证：修改同一个招式文件，训练场与 Solver 都使用该变化。

下表为用于讨论的实施切片，不是已发布或可直接领取的 issue。正式拆分时根据规则复杂度调整；第 1 阶段已经完成的工作记为已完成，不重复实施。

完成条件：每个正式 issue 有可演示行为、明确验收、真实阻塞关系和必要规则上下文；可以在新的实现任务中独立理解。

**5. 每个 issue 使用 `/implement`，按依赖推进**

执行循环：读取 issue 和相关规则 → 在现有公开边界验证行为 → 实现一个完整切片 → 运行相关检查 → `/code-review` 检查规格与项目约定 → 修正发现 → 提交并更新 issue 记录。

涉及复杂规则或故障回归时使用 `/tdd`；简单布局、说明修改做相应的视觉或内容检查。测试不能只给识别器喂最终招式名，必须覆盖实际方向与动作输入经过训练场适配、识别、缓存、取消到执行的路径。

完整规则讨论、规格与拆单尽量保留在同一任务上下文中；实现阶段每个 issue 可单独开任务，只携带正式 issue 及其引用材料。创建这些任务由实际执行请求触发，本路径本身不创建新任务。

**6. 联合验收和手感回调**

| 验收场景 | 要观察的结果 |
| --- | --- |
| 跳跃后松开方向、按反向、搓招和空中出招 | 水平输入不改变普通空中运动与面向；配置的招式运动和碰撞按规则单独处理 |
| 左右面向地面/空中方向派生 | 物理键、相对方向、识别招式与实际执行一致 |
| Hitstop 开始、最后一帧与结束边界输入 | 停顿期间运动/阶段按规则冻结，输入按规则保留，恢复后只消费合资格操作 |
| 起跳准备、离地首帧、落地首帧与 jump cancel | 姿态、攻击可用时点、取消和有限空中资源符合帧表 |
| 站防/蹲防/空防与各攻击属性、普通投 | 防御矩阵、硬直、停顿、投与拆投结果可重复；用木桩配置或确定性攻击脚本提供测试条件 |
| 修改本地招式文件 | 训练场与 Solver 结果一致变化；非法数据给出明确原因 |
| 按 Solver 说明重放地面、空中、jump cancel 和落地路线 | 操作说明与实际按键对应；注明起始位置/面向和已验证范围；未通过空间验证的结果不宣称空间可达 |

先通过确定性验证，再由真人试玩调整首版参数。修改会影响连段的帧数或条件后，重新运行受影响的战斗与 Solver 验证。最终更新操作说明、招式/行为表、Solver 使用示例和 issue 验收记录。
