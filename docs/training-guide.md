# 训练场操作与联合验收

更新于 2026-09-18。规则以 `.scratch/ftg-combat-foundation/spec.md` 为准；旧 issue 的逐阶段实现记录不是规则例外。

## 启动与操作

Godot 4.5.1 打开 `project.godot` 后按 F5。运行时 R 重置场景；修改 `.tres` 后须退出游戏并重新运行，R 不保证绕过资源缓存。

| 操作 | 物理输入 |
| --- | --- |
| 移动、蹲下 | A/D 或 ←/→；S 或 ↓ |
| 跳跃 | Space 或 ↑；与前/后组合为 9/7，上下同时按中和 |
| 动作 A/B/C/D | U/I/K/J |
| 236C，面向右 | S → S+D → D，再按 K |
| 236C，面向左 | S → S+A → A，再按 K |
| 214D，面向右 | S → S+A → A，再按 J |
| 214D，面向左 | S → S+D → D，再按 J |
| 站防、蹲防、空防 | 相对后 4、下后 1；空中 4/1 均为空防 |
| 前冲、后撤 | 相对 66/44，两段间至少一帧中立 |
| 普通投 | I+K，两个新按下相差 ≤3 物理帧，配齐时都保持按住；中心距离 ≤64px |
| 木桩防御 | G 循环 无 → 站防 → 蹲防 → 空防（逐帧确定性请求；木桩无自主决策） |

物理 D 是“向右”，动作 D 对应物理 J。方向数字按面向折算。地面自由行动时面向木桩，后退不转身；普通跳离地后松开、反向或搓招不改变起跳横向运动和面向。空中方向派生依资源配置；默认表没有 j214D，自动化用临时合法表验证它，不能把默认 jD 当成空中搓招成功。

单独 I/K 最多多等 3 个物理帧配对；U/J 不等待。命中后后续 8 个物理帧冻结，输入仍采样。动作缓存年龄 0–5 有效，6 过期；命中确认取消年龄 0–8 有效，9 关闭，均不计 Hitstop。跳跃为准备 4f、空中 38f、落地基础 3f；启动空中技后落地至少 4f。落地首帧一律不能启动攻击，空技恢复全程锁定，即使资源写了 landing_cancel_targets 也不能例外。

默认木桩不主动攻击，也不自动拆投。防御矩阵和拆投由确定性测试的 `dummy_move_request` / `dummy_tech_request` 驱动；木桩防御自票据 03 起由 G 键训练模式或测试的 `dummy_guard_request` 逐帧请求驱动（NONE/STAND/CROUCH/AIR）——挡下玩家攻击产生 ATTACK_BLOCKED 事件，HUD 事件行显示「攻击被站防挡下（被防硬直 N）」，被防硬直期间木桩姿态冻结（连防）且不出招；请求与地面/空中状态不符（如地面请求空防）或木桩受击/倒地/出招中时给出可观察拒绝原因，不静默回退其他防御。玩家被投和玩家主动拆投不是当前可用的人机功能。

蹲下时原地停住：S/↓ 与左、右同时按也不移动；从行走切入蹲姿时立即停止滑行，松开下方向后恢复移动。下后仍可蹲防，下前/下后的方向仍用于搓招。受击击退和空中运动遵循各自规则。此为 2026-09-18 真人反馈后的修复，重新运行项目生效。

## 确定性验收入口

在项目目录运行 `./tools/run_acceptance.ps1`。它导入项目、运行全部 `tests/test_*.gd`、输入诊断和 300 帧冒烟，输出逐项退出码及脚本错误检查。测试用户数据和日志放在项目内，避免默认用户目录写权限导致引擎启动失败。

专项入口：

```powershell
$env:APPDATA = "$PWD/.scratch/ftg-combat-foundation/acceptance-2026-09-17/runtime"
& D:/Godot/Godot_v4.5.1-stable_mono_win64_console.exe --headless --path . --log-file .scratch/ftg-combat-foundation/acceptance-2026-09-17/engine.log -s res://tests/test_replay_acceptance.gd
```

训练场测试注入 Godot 输入映射并推进物理帧；它不等于真人按键，也不测外设延迟。回放数据和站位边界见 [Solver 使用说明](solver-guide.md)。

## 真人试玩反馈与复玩记录单

2026-09-18 用户报告：当前手感可接受，各项测试条目顺利通过，发现蹲姿仍可移动。本次已修复蹲姿移动，完整自动化回归通过；尚未收到修复后的真人复玩反馈。没有提供外设、试次或成功率明细，以下保留为可重复记录模板，不补填未报告的数据。

复玩时先检查：左右面向分别按住下前/下后保持原地；行走中按下立刻停止；松开下后移动恢复；236C/214D 仍可识别。需要量化时记录日期、操作者、窗口尺寸、键盘、面向、站位、尝试数、成功数、过早/过晚/误识别和主观迟滞。

1. 左右面向各做前跳松开、反向、搓招和空中出招，分别至少 5 次；区分输入改变速度与碰撞/招式运动的影响。
2. 地面 236C/214D 各侧各 10 次，比较 U/J 与 I/K 单键响应；I+K 组合与快速分开按各 10 次，记录等待 3f 的迟滞和 ≤3f 容差的漏识别。
3. 命中/挥空结果未知的试次各至少 10 次，命中后才主动接续，记录成功率和误接。该项需要主持者或盲测驱动在攻击前隐藏试次结果；独自重复固定站位不能冒充此项。
4. 按 Solver 表练地面路线（70px）和空中路线（48px），分别记录左右面向结果；禁止把 70px 空中五连列为已验证可达。
5. 观察准备 4f、Hitstop 8f、缓存 6f 的反馈；空技落地恢复期间输入与恢复后新输入对比。帧边界以自动化日志为准，人眼不能精确证明单帧。
6. 在有确定性木桩攻击/拆投请求的测试场景中试玩站防、蹲防、空防和投；普通场景没有该请求入口，本项仍需交互驱动。检查 960×540 和常用窗口尺寸的 HUD；项目无音效，因此无音画同步通过结论。

当前不调整参数。若真人明确报告停顿拖沓，先只比较 Hitstop 8→6f；若报告过早输入丢失，固定其他条件比较缓存 6→7f；若报告 I/K 单键迟滞，比较组合等待/容差 3→2f 并同时统计拆分组合失败率。这些是条件化试验建议，尚未获采纳；每次仅改变一项并重跑战斗、训练场和 Solver 验证，不能改结算顺序来改善手感。
